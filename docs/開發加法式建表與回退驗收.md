## 2. 隔離資料與比對方式

- [歷史 fixture](../test/test_development_schema_lifecycle.py:63)只在每例暫存庫複製兩張既有快照表，加入合成歷史文件及成本列。沒有主檔可供重算，沒有真實客戶資料。
- 使用[既有成本讀取入口](../database/repository.py:484)，完整歷史文件則透過[既有文件模型](../database/models.py:284)原字串讀取，不另寫一個假歷史讀取器取代應用行為。
- 覆蓋兩個事業別共用同一舊單號、相同路徑不同成本列、反向插入但按五位序號讀取、零成本與缺值、沒有完整文件的早期列式歷史。原始文件的空白、換行、精確數字字串及控制字元不重編碼或回填。
- 比對實際資料庫的建表／索引定義、所有舊表欄位值及讀取結果；不只比較 ORM 宣告或資料筆數。
- 新資料沿用[合成四品項請求](../test/development_atomic_fixtures.py:19)及[隔離子程序](../test/development_process_worker.py)，驗證四張／11 件、來源與共用／專屬原文、原保留號、建立時間、精確金額及整批／逐張輸出。

**相容性證據僅限目前程式中的既有 repository／ORM 入口。** 本批沒有安裝或啟動某個過往發布版本，不能宣稱所有舊版應用、舊版依賴或實際降版部署均已驗收。

## 3. 驗收矩陣

| 情境 | 驗證內容 |
|---|---|
| 只有兩張歷史表，DELETE／WAL | 明確新增六張開發表；舊表結構、索引、逐欄資料與讀取結果不變 |
| 已有完整配號保留，DELETE／WAL | 只新增四張開發快照表，registry 不變；後續保存仍使用原保留 |
| 重跑建表 | 已有表、索引與資料不變；原請求跨程序重試禁止讀時鐘，仍回原完整文件與輸出 |
| 歷史與開發資料共存 | 舊入口不把開發保留號讀成舊單品快照；不回填舊文件或新關聯 |
| 六張新增表各個建表後注入失敗 | 明確 SQLite 實體交易下，新表全部回滾，原歷史表保留；後續明確重試可成功 |
| 已保留後，第二／第四張開發表建表失敗 | 四表升級回滾，已提交 registry 與號碼仍保留，不回收孤兒保留 |
| 停用新功能後只讀舊資料 | 檔案唯讀連線加資料表讀取允許清單；舊查閱正常，新表查詢與舊表刪除實際遭拒絕 |
| 保留中／已保存狀態停用再啟用 | 不刪表、不換庫、不還原舊備份；原保留與已保存文件仍可由原請求查回 |
| 未建表、只有 registry、只建部分表 | 缺表錯誤不被保存服務吞成成功，也不隱式建表；部分寫入回滾 |
| 同名表欄位已漂移 | 重跑建表不修復漂移；讀取／保存缺欄位錯誤明確傳出，歷史資料不變 |
| 不支援的持久文件版本 | 配號保留或批次版本異常時查閱／保存拒絕，不翻版本、重寫或自動降版 |
| 刪成本表後重建空表，僅破壞備份 clone | 結構及外鍵檢查仍可通過，但完整查閱／保存拒絕缺列，不補算或修補；來源庫不變 |

## 4. 三個不可誤讀的限制

### 建表交易必須驗證實體行為

[測試專用建表 helper](../test/test_development_schema_lifecycle.py:112)明確開始 SQLite 實體寫交易，再建立所選新表；例外時全部回滾。這只證明本次 macOS／SQLite／driver 組合的行為，不能直接移植為 MySQL／MSSQL 的交易式遷移承諾。

[反例測試](../test/test_development_schema_lifecycle.py:321)證明目前 SQLite 舊交易模式下，只有 SQLAlchemy 外層交易區塊、尚未開始實體交易時，建表可能已提交，之後的例外不會移除該表。不能看到程式有交易區塊就宣稱遷移原子性。

### 表存在、查無資料與健康檢查都不是部署核准

[欄位漂移測試](../test/test_development_schema_lifecycle.py:298)確認既有建表檢查只依表名跳過，不驗證或修改既有欄位。正式部署仍須比對現場欄位型別、容量、索引、唯一鍵、外鍵及版本，不能靠應用啟動建表完成遷移。

[缺表測試](../test/test_development_schema_lifecycle.py:272)亦保留目前服務界線：空的批次表可能讓讀取回傳查無資料，而沒有碰到尚未建立的子表。**單次查無快照不是完整 schema readiness 檢查**；保存碰到缺表時仍須失敗，不可據此開放正式寫入。

[重建空表反例](../test/test_development_schema_lifecycle.py:335)證明結構檢查通過不代表快照完整；建表不是還原，缺列不能靠重新計價或重新配號補救。

### 回退只驗證保留資料的停用方式

[停用回退測試](../test/test_development_schema_lifecycle.py:183)模擬「停止呼叫新功能，僅保留受限舊讀取」，不新增部署功能開關，也不操作正式環境。重新啟用後用原身份／原請求查回，不能將查不到舊資料解讀為可重新發號。

有新保留或快照後，禁止以刪表、覆寫歷史、搬入舊成本表或恢復遷移前備份作為便捷回退。回退應先停止新寫入並保留資料及證據；若需還原，另依[備份最新性與權威配號對帳限制](開發備份還原驗收.md)辦理。

## 5. 正式待辦

1. DBA 核准實際遷移清單、schema 前置比對、遷移版本紀錄、權限、鎖等待及失敗處理；本批沒有新增正式 migration runner 或 schema readiness 服務。
2. 以指定過往發布版本及其依賴驗證舊讀取、啟動副作用、停用方式與重新部署；本批不是實際二進位／套件降版演練。
3. 正式資料寬度、精確小數儲存與新版正式文件契約；不能將較寬開發欄位截短或將精確字串轉浮點搬入歷史表。
4. 遷移前後受控備份、最新權威 registry 對帳、復原点與時間目標，以及來源庫與還原庫不可同時配號的隔離規範。
5. Windows、主機斷電、磁碟故障、MySQL／MSSQL runtime、跨庫故障切換與正式授權驗收。
