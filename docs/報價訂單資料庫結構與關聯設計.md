# 報價／訂單產品選配資料庫設計文件

> 目的：整理目前從既有資料字典畫面確認的 `ordspd`、`ordspe`、`ordqty` 結構，以及後續建議新增的報價規格明細 `ordqdt`，供後續程式開發、SQL 建模與報價／訂單流程設計使用。
>
> **重要說明**：`ordspd`、`ordspe`、`ordqty` 的欄位資訊與 Key 主要依目前提供的資料字典截圖整理；資料表之間的外鍵關係、部分業務語意屬於依欄位名稱與實際資料推導的「建議關係」，正式開發前應再以現行程式 SQL／實際資料驗證。

---

## 1. 整體業務目的

系統需要依據：

1. 產品有哪些部件
2. 每個部件需要多少標準用量／裁切量
3. 每個部件可以選擇哪些項目
4. 使用者實際選擇的規格
5. 各選項當時的採購成本
6. 報價規則與加成

產生客戶報價，報價確認後再轉成正式訂單。

建議的資料流：

```text
產品／部件
   │
   ▼
ordqty
部件用量規則
   │
   ├──────────────┐
   ▼              ▼
ordspe           ordspd
可選項目          選項定義
   │              │
   └──────┬───────┘
          ▼
       ordqdt
   報價實際選擇明細
          │
          ▼
      報價計算
          │
          ▼
      報價單／報價明細
          │
       確認報價
          │
          ▼
       訂單主檔
       訂單明細
```

---

# 2. 資料表總覽

| 資料表 | 建議用途 | 核心角色 |
|---|---|---|
| `ordspd` | 選項定義檔 | 定義「有哪些選項類別」 |
| `ordspe` | 可選項目檔 | 定義「某選項底下有哪些項目、採購成本」 |
| `ordqty` | 產品部位用量檔 | 定義「某項目／部位需要多少用量」 |
| `ordqdt` | 報價規格明細檔 | 記錄「本次報價實際選了什麼」 |

其中 `ordqdt` 是後續建議新增的資料表。

---

# 3. ordspd — 選項定義檔

## 3.1 用途

`ordspd` 用來定義系統中的選項類別。

例如：

```text
桌面尺寸
木腳尺寸
轉盤尺寸
美耐板
顏色材質
上板
下板
立水
...
```

它回答：

> 「這個產品有哪些可以讓使用者選擇的規格類別？」

## 3.2 欄位

| 欄位 | 中文 | 型態 | Null | 長度 | 說明 |
|---|---|---|---|---:|---|
| `workgroup` | 事業別 | NChar | N | 3 | 事業別 |
| `kind` | 類別 | NChar | Y | 1 | 選項類別 |
| `optno` | 代碼 | NChar | N | 10 | 選項代碼 |
| `optdesc` | 說明 | NChar | Y | 30 | 選項說明 |
| `code` | 編碼 | NChar | Y | 10 | 選項相關編碼 |
| `adddate` | 建立日期 | Char | Y | 10 | 建立日期 |
| `addusrno` | 建立人員 | Char | Y | 8 | 建立人員 |
| `abndat` | 異動日期 | Char | Y | 10 | 異動日期 |
| `abntim` | 異動時間 | Char | Y | 8 | 異動時間 |
| `usrno` | 異動人員 | Char | Y | 8 | 異動人員 |
| `prgno` | 異動程式 | Char | Y | 10 | 異動程式 |

## 3.3 Primary Key

依資料字典畫面：

```text
(workgroup, optno)
```

建議 SQL：

```sql
PRIMARY KEY (workgroup, optno)
```

## 3.4 角色

```text
ordspd
   │
   ├── optno = A001
   │      └── 桌面尺寸
   │
   ├── optno = B001
   │      └── 木腳尺寸
   │
   └── optno = S005
          └── 顏色材質
```

# 4. ordspe — 可選項目記錄檔

## 4.1 用途

`ordspe` 是 `ordspd` 定義的選項之下，實際可以選擇的項目。

例如：

```text
選項：桌面尺寸

A001 → 桌面尺寸
B001 → 木腳尺寸
S005 → 顏色材質
```

實際資料中 `path` 具有階層式路徑特性，例如：

```text
CMT1\A001
CMT1\A001\W001
CMT1\A001\W001\W040
```

因此 `path` 很可能同時負責描述產品／選項階層。

## 4.2 欄位

| 欄位 | 中文 | 型態 | Null | 長度 | 說明 |
|---|---|---|---|---:|---|
| `workgroup` | 事業別 | NChar | N | 3 | 事業別 |
| `path` | 路徑 | NChar | N | 100 | 選項階層路徑 |
| `code` | 項目編號 | NChar | N | 10 | 項目代號 |
| `codsc` | 項目名稱 | NChar | N | 40 | 項目名稱 |
| `compri` | 採購單價 | Float | Y | 8 | 採購成本 |
| `adddate` | 建立日期 | Char | Y | 10 | 建立日期 |
| `addusrno` | 建立人員 | Char | Y | 8 | 建立人員 |
| `abndat` | 異動日期 | Char | Y | 10 | 異動日期 |
| `abntim` | 異動時間 | Char | Y | 8 | 異動時間 |
| `usrno` | 異動人員 | Char | Y | 8 | 異動人員 |
| `prgno` | 異動程式 | Char | Y | 10 | 異動程式 |

## 4.3 Primary Key

依目前畫面 Key 標示：

```text
(workgroup, path, code, codsc)
```

## 4.4 角色

```text
ordspd
   │
   │ optno
   ▼
ordspe
   │
   ├── path
   ├── code
   ├── codsc
   └── compri
```

`compri` 建議視為「目前採購成本」，而不是直接視為客戶報價。

# 5. ordqty — 產品部位用量記錄檔

## 5.1 用途

`ordqty` 用來描述產品／項目與部位之間的用量關係。

例如：

```text
桌面
 ├── 標準量 = 1
 └── 裁切量 = 1

木腳
 └── 標準量 = 4

立水
 └── 標準量 = 2
```

它回答：

> 「這個產品部位需要多少材料或用量？」

## 5.2 欄位

| 欄位 | 中文 | 型態 | Null | 長度 | 說明 |
|---|---|---|---|---:|---|
| `workgroup` | 事業別 | NChar | N | 3 | 事業別 |
| `path` | 路徑 | NChar | N | 100 | 項目階層路徑 |
| `code` | 項目編號 | NChar | N | 10 | 項目代號 |
| `codsc` | 項目名稱 | NChar | Y | 40 | 項目名稱 |
| `part_path` | 部位路徑 | NChar | Y | 100 | 產品部位路徑 |
| `stdqty` | 標準量 | Float | Y | 8 | 標準用量 |
| `stdpar` | 裁切量 | Float | Y | 8 | 裁切用量 |
| `adddate` | 建立日期 | Char | Y | 10 | 建立日期 |
| `addusrno` | 建立人員 | Char | Y | 8 | 建立人員 |
| `abndat` | 異動日期 | Char | Y | 10 | 異動日期 |
| `abntim` | 異動時間 | Char | Y | 8 | 異動時間 |
| `usrno` | 異動人員 | Char | Y | 8 | 異動人員 |
| `prgno` | 異動程式 | Char | Y | 10 | 異動程式 |

## 5.3 Primary Key

依目前畫面：

```text
(workgroup, path, code, codsc)
```

## 5.4 與 ordspe 的關係

`ordspe` 與 `ordqty` 具有相同的：

```text
workgroup
path
code
codsc
```

因此在目前資料結構下，可推定兩者具有邏輯關聯：

```text
ordspe
   │
   │ (workgroup, path, code, codsc)
   │
   ▼
ordqty
```

但正式程式開發前，應確認現有資料庫是否真的建立 Foreign Key；不能只因欄位相同就假設資料庫層已有 FK。

# 6. ordqdt — 報價規格明細檔（建議新增）

## 6.1 設計目的

`ordqdt` 是建議新增的「報價實際選擇結果」資料表。

它與主檔最大的不同：

```text
ordspe = 現在系統有哪些可選項目
ordqdt = 這一張報價當時實際選了哪些項目
```

這是避免歷史報價被主檔異動影響的關鍵。

## 6.2 建議欄位

| 欄位 | 中文 | 型態 | Null | 說明 |
|---|---|---|---|---|
| `workgroup` | 事業別 | NChar(3) | N | 事業別 |
| `ref_no` | 報價單號 | NChar(21) | N | 報價／訂單識別 |
| `seq_no` | 明細序號 | NChar(5) | N | 明細排序 |
| `part_code` | 部件代碼 | NChar(10) | N | 部件識別 |
| `part_desc` | 部件名稱 | NChar(40) | Y | 報價當時部件名稱 |
| `path` | 挑選路徑 | NChar(100) | N | 選配路徑 |
| `opt_code` | 選項代碼 | NChar(10) | Y | 對應 `ordspd.optno` |
| `opt_desc` | 選項說明 | NChar(40) | Y | 報價當時選項名稱 |
| `spc_code` | 規格代碼 | NChar(10) | Y | 規格代碼 |
| `spdsc` | 規格 | NChar(40) | Y | 報價當時規格名稱 |
| `qty` | 數量 | Decimal | Y | 實際數量 |
| `stdqty` | 用料量 | Float | Y | 標準用量快照 |
| `stdpar` | 裁切量 | Float | Y | 裁切量快照 |
| `compri` | 採購成本 | Float | Y | 報價當時成本快照 |
| `unit_price` | 報價單價 | Float | Y | 客戶實際報價單價 |
| `amount` | 報價金額 | Float | Y | 明細金額 |
| `unit` | 單位 | NChar(5) | Y | PCS、SET、M 等 |
| `status` | 狀態 | NChar(1) | Y | 草稿／確認／作廢 |
| `adddate` | 建立日期 | Char(10) | Y | 建立日期 |
| `addusrno` | 建立人員 | Char(8) | Y | 建立人員 |
| `abndat` | 異動日期 | Char(10) | Y | 異動日期 |
| `abntim` | 異動時間 | Char(8) | Y | 異動時間 |
| `usrno` | 異動人員 | Char(8) | Y | 異動人員 |
| `prgno` | 異動程式 | Char(10) | Y | 異動程式 |

## 6.3 Primary Key

建議：

```text
(workgroup, ref_no, seq_no)
```

而不是使用：

```text
(workgroup, ref_no, path, spc_code)
```

原因是同一部件／同一路徑／同一規格未來可能出現多筆明細。

## 6.4 qty 欄位建議

目前截圖中的 `qty` 是：

```text
NChar(1)
```

如果要支援正式報價計算，建議改成：

```sql
DECIMAL(12,3)
```

如果業務規則保證只能使用整數，可以使用：

```sql
INT
```

不建議使用 `NChar(1)` 儲存數量。

# 8. 報價產生流程

## Step 1：建立報價單

建立：

```text
ref_no = Q20260818001
```

## Step 2：取得產品部件

依產品取得相關 `ordqty`。

例如：

```text
桌面
木腳
立水
下板
```

## Step 3：取得可選項目

依 `path` 找到 `ordspe`。

例如：

```text
桌面
 ├── 桌面尺寸
 ├── 桌面外型
 └── 顏色材質
```

## Step 4：使用者選擇規格

例如：

```text
桌面尺寸 → 1200 × 600
桌面外型 → TOP
顏色材質 → 美耐板
木腳 → B001
```

## Step 5：寫入 ordqdt

將使用者選擇結果寫入：

```text
ref_no
seq_no
part_code
path
opt_code
spc_code
qty
stdqty
stdpar
compri
```

## Step 6：計算成本

基本概念：

```text
成本 = 數量 × 用量 × 採購單價
```

實際公式要依公司裁切／材料計價規則調整。

## Step 7：計算報價

例如：

```text
成本
 ↓
加成率
 ↓
折扣
 ↓
報價單價
 ↓
報價金額
```

`ordqdt` 建議保留：

```text
compri
unit_price
amount
```

形成歷史快照。

---

# 9. 為什麼要保存報價快照

假設今天：

```text
ordspe.compri = 500
```

客戶報價：

```text
unit_price = 800
```

建立報價：

```text
Q20260818001
成本 = 500
報價 = 800
```

一個月後主檔成本變成：

```text
ordspe.compri = 550
```

舊報價：

```text
Q20260818001
```

仍然必須保持：

```text
成本 = 500
報價 = 800
```

所以：

```text
ordspe.compri
```

是「目前主檔成本」。

而：

```text
ordqdt.compri
```

是「建立該報價時的成本快照」。

兩者不能混為一談。

---

# 10. 建議不要把報價與主檔直接綁死

錯誤設計：

```text
報價畫面
   ↓
每次重新查 ordspe.compri
   ↓
重新計算舊報價
```

這會造成歷史資料錯誤。

建議：

```text
ordspe
目前主檔
   │
   │ 建立報價時複製
   ▼
ordqdt
歷史快照
   │
   ▼
報價
```

# 12. 建議的 SQL 查詢方向

## 12.1 取得某路徑可選項目

```sql
SELECT
    workgroup,
    path,
    code,
    codsc,
    compri
FROM ordspe
WHERE workgroup = :workgroup
  AND path = :path
ORDER BY code;
```

## 12.2 取得某項目的用量

```sql
SELECT
    workgroup,
    path,
    code,
    codsc,
    part_path,
    stdqty,
    stdpar
FROM ordqty
WHERE workgroup = :workgroup
  AND path = :path
  AND code = :code
  AND codsc = :codsc;
```

## 12.3 建立報價明細

概念上：

```sql
INSERT INTO ordqdt (
    workgroup,
    ref_no,
    seq_no,
    part_code,
    part_desc,
    path,
    opt_code,
    opt_desc,
    spc_code,
    spdsc,
    qty,
    stdqty,
    stdpar,
    compri,
    unit_price,
    amount
)
VALUES (
    :workgroup,
    :ref_no,
    :seq_no,
    :part_code,
    :part_desc,
    :path,
    :opt_code,
    :opt_desc,
    :spc_code,
    :spdsc,
    :qty,
    :stdqty,
    :stdpar,
    :compri,
    :unit_price,
    :amount
);
```

# 14. 建議增加的索引

大量產品與報價資料下，建議至少：

```sql
CREATE INDEX idx_ordspe_path
ON ordspe(workgroup, path);

CREATE INDEX idx_ordqty_path
ON ordqty(workgroup, path);

CREATE INDEX idx_ordqty_part
ON ordqty(workgroup, part_path);

CREATE INDEX idx_ordqdt_ref
ON ordqdt(workgroup, ref_no);

CREATE INDEX idx_ordqdt_part
ON ordqdt(workgroup, ref_no, part_code);
```

實際索引仍應依正式查詢 SQL 與資料量調整。

# 15. 目前尚待確認的資料

以下項目目前不能單靠截圖 100% 確認，開發前應查現有程式與資料：

1. `ordspd.code` 與 `ordspe.code` 是否有正式 FK。

9. 報價轉訂單時，哪些欄位需要複製。
10. 現有系統是否已經有 `ref_no` 的編號產生規則。

# 16. 建議後續確認順序

為了避免直接開始寫程式後才發現資料關係不正確，建議依序確認：

```text
① ordspd
   ↓
② ordspe
   ↓
③ ordqty
   ↓
④ 實際產品／部件資料
   ↓
⑤ 報價主檔
   ↓
⑥ 報價明細
   ↓
⑦ 訂單主檔
   ↓
⑧ 訂單明細
```

尤其下一步最好取得：

```text
ord940
ord920
```

以及目前報價／訂單相關的資料表結構。

這樣可以把目前「推定的關係」改成「實際資料庫關係」。

---

# 17. 開發時的核心原則

### 原則 1：主檔與歷史報價分離

```text
ordspe.compri
    = 現在採購成本

ordqdt.compri
    = 報價建立當時成本
```

### 原則 2：報價必須保存快照

報價確認後，不應因產品主檔修改而改變歷史報價。

### 原則 3：數量使用數值型態

不要使用：

```text
NChar(1)
```

建議：

```text
DECIMAL(12,3)
```

### 原則 4：明細使用 seq_no

不要依賴產品名稱、路徑或規格作為報價明細唯一識別。

### 原則 5：報價與訂單分開

```text
報價
  ↓ 確認
訂單
```

不要直接把「報價資料」當成「訂單資料」。

## 19. 結論

目前已確認的核心資料表可以定位為：

```text
ordspd
  = 「選項類別定義」

ordspe
  = 「選項底下有哪些可選項目」

ordqty
  = 「產品／部件需要多少用量」

ordqdt
  = 「這張報價實際選了哪些項目」
```

其中最重要的設計觀念是：

```text
主檔資料
     ↓
產生報價
     ↓
複製成報價快照
     ↓
報價確認
     ↓
產生訂單
```

而不是在訂單／歷史報價中持續依賴目前的 `ordspe`、`ordqty` 主檔資料。

這樣後續即使產品、選項、採購成本、用量規則修改，也能維持歷史報價與訂單的一致性。
