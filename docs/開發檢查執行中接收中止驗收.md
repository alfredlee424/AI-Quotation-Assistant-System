## 2. 真實程序與同步

- [隔離 worker](../test/development_reception_worker.py)沿用原受控接收入口，由原收集器建立獨立存檔群組，再啟動同群組的真正檢查子程序。
- [存檔測試同步工具](../test/development_active_reception_hooks.py)只對本批階段傳遞兩個測試控制描述符；原四階段不改變。
- [檢查測試同步點](../test/development_live_inspection_hooks.py)在原匯入前防護安裝後注入，呼叫原表結構讀取函式，**完成第一張受檢表的結構讀取後**才停止。排除私有記憶體參考庫，不替換 SQL、檢查結果、報告、回條或退出碼。
- 控制管線傳回檢查程序識別；父測試確認接收、存檔、檢查為不同程序，檢查確實屬於存檔群組，再進行中止或放行。不靠任意延遲猜測執行階段。
- 檢查與存檔均持控制寫端，群組中止後有界等待控制 EOF；不能只等存檔 leader 結束。存檔函式返回標記仍不是孤兒存檔程序的 OS 退出證明。
- 保留原私人檔案、網路、正式依賴與額外子程序防護。測試只用工作區外合成 SQLite、四品項／11 件資料與私有目的目錄，不讀私人設定或工單日誌、不連 ERP／真模型、不執行正式建表。

## 4. 故障判讀

| 動作 | 報告／接收結果 |
|---|---|
| 接收者死亡後，外部明確終止存檔群組 | 無報告、無暫存、無接收紀錄；原缺件離線核驗拒絕 |
| 接收者死亡後，允許真正檢查繼續 | 仍可完成檢查並發布完整私有報告；回條輸出失敗，存檔函式返回 3；沒有接收紀錄，不降級核驗 |
| 接收者死亡後，只終止檢查程序 | 原收集器拒絕訊號退出；無報告、無接收紀錄，不提供部分結果 |
| 接收者死亡後，新執行先發布，再放行舊檢查 | 新報告及接收紀錄保持全部位元組不變；舊存檔無覆寫發布拒絕，只清理自身暫存 |
| 檢查持讀交易不放行，原收集期限到期 | 原收集器終止並等待檢查程序；無報告、無接收紀錄。接收者仍活著時實際退出 3 |
| 存檔 leader 死亡，但檢查後代仍持輸出管線 | 活著的接收者期限到期後清理自有群組，實際退出 3，不把 leader 死亡當作管線已完成 |

父測試的外部群組清理不是死亡接收者執行清理，也不是新增應用自動取消能力。明確使用新名稱重跑是新執行，不是替舊執行補建回條或接收紀錄。

## 5. 讀鎖與新鮮度

DELETE 模式下，檢查屏障仍持有真實讀交易，另一個零等候連線申請排他交易會收到資料庫忙碌；檢查退出或群組清理後，排他交易可成功並立即回滾，未寫入資料。這驗證該同步點確實持有讀鎖及清理後釋放，不是所有鎖等待情境的認證。

WAL 模式下，檢查讀取第一端後，父測試可在另一連線刪除該端整組資料並提交。當次仍可產生無差異報告：第一端是固定舊快照，第二端仍是原完整內容。下一次明確執行則產生差異報告。接收者存活時，舊報告與接收紀錄也仍可通過離線核驗；接收者死亡時，只有報告而缺紀錄仍拒絕。

**讀取一致不是停寫、跨庫同一復原點或最新性證明；完整接收與離線核驗也不會使舊報告自動更新。**
