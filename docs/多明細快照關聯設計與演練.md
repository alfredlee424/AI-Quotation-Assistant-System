## 1. 本批目的與界線

2026-09-30 補上 T07／T29 的快照關聯基礎，以及 T31 的部分序號容量、資料表約束與新舊入口隔離測試。

每筆產品可能有相同部位路徑。組裝時必須先以穩定產品明細識別隔離，再在該明細內用部位與規格代碼定位；不能把不同桌面的同一路徑去重成一列，也不能把產品明細識別塞進 ERP 路徑。

**本批只提供非正式關聯演練，以及待 DBA 審查的加法式表結構契約。** 不產生正式單號、不開放兩次確認、不保存資料庫、不執行正式遷移，不表示 T07／T29／T31 已全面完成。

## 2. 操作方式

1. 進入「多明細配置草稿」，完成配置並填寫操作人。
2. 在「多明細內部試算與整單折扣」明確執行一次內部試算。
3. 展開「多明細快照關聯演練（不可正式保存）」。
4. 按「產生快照關聯演練（不查價、不保存）」。
5. 核對產品明細、排列順序、對應列數、全單序號及原始部位路徑。
6. 檢查未試算明細、封存明細、欄位容量問題及展示金額差額。
7. 如需內部或 DBA 審查，可下載「快照關聯演練（不可保存為報價）」。

未執行內部試算時不提供演練按鈕。演練與畫面重新顯示都只使用既有固定試算，不重新查主檔、不重算成本、不開啟資料庫連線。

下載包含成本、單價、用量、圖面摘要及需求核對資料，應依公司資料政策保存；不是可交給客戶的報價，也不支援重匯入。圖面及人工核對資料不會加入模型上下文。

## 3. 組裝契約

### 3.1 產品層

每筆活動產品明細保留：

- 穩定產品明細識別、明細版本與本次展示順序。
- 產品類別、名稱、成品數量及試算狀態。
- 該產品本身的報價係數、成本、小計及未捨入中間值。
- 其快照列序號清單。

未試算的明細保留在產品清單，並另外列出未包含原因，不會默默略過或補零價。

### 3.2 明細列與關聯層

- 每列由「產品明細識別＋原始完整部位路徑」定位。
- 同一產品明細的同一路徑只能出現一次；其他產品明細可使用相同路徑，甚至相同規格代碼。
- 成本列的產品明細識別、部位與規格代碼，必須與同一筆固定選配完全對應。
- 成品數、每件項目數與實際數量分別保存並核對，不混用。
- 保留用量來源、驅動部位及驅動規格；驅動必須屬於該產品自己的固定選配。
- 固定選配與成本列須完整雙向覆蓋；零價、零用量及結構節點也不能漏掉。缺列時拒絕整次演練，不以預設零價補齊。
- 全單快照序號從 00001 到 99999，每列唯一；超過上限則整次拒絕，不截斷、不循環、不重用序號。
- 明細重排後序號可以重新編排，穩定產品明細識別不變。序號不是跨版本的產品識別。

演練列刻意不含正式單號、已確認狀態或可直接寫入的稽核人員欄位，不能交給舊單品保存入口。舊入口會在開啟資料庫前拒絕多明細／內部試算／關聯演練文件或帶有多明細關聯的列。

### 3.3 金額與捨入

成本、單價、金額、逐產品係數及整單結果全部來自同一份固定試算。演練不重新加成、不逐列分攤整單折扣與稅，也不調整展示列去湊總額。

例如兩列原始金額各 0.335，展示各 0.34，逐列展示加總為 0.68，而未捨入整單小計為 0.67。畫面揭露 0.01 差額，保留各列及整單原結果。

## 4. 容量與版本保護

目前依既有 ORM 欄位及新表草案，檢查文字容量，不截斷值：

| 欄位類別 | 目前限制 |
|---|---|
| 快照列序號 | 5 字，最多 99999 列 |
| 完整部位路徑 | 100 字 |
| 部件／選項／規格代碼 | 10 字 |
| 部件／選項／規格說明 | 40 字 |
| 單位 | 5 字 |
| 既有建立人代碼 | 8 字 |
| 新表產品明細識別 | 32 字 |
| 新表產品名稱 | 200 字 |

共用操作人允許 80 字，但既有建立人欄位只有 8 字。演練會揭露不相容並完整保留操作人，不自行截短或偽造員工代碼。正式保存前需核准「操作人身分到正式人員代碼」的映射制度。

容量檢查只以目前 ORM 的字元長度為基礎；不能推論所有資料庫的位元組限制、字元編碼、定序或索引限制已通過。正式部署須另行驗證。

- 草稿、試算、操作人、圖面或關聯契約改變，都會使舊演練失效。
- 即使草稿未變，重新內部試算也會產生新試算識別，舊演練不能沿用。
- 任何列、關聯、金額或文件狀態被修改，都不能作為原演練下載。
- 產生失敗會清除舊結果；不以舊演練掩蓋本次錯誤。
- 有未試算或封存明細時只保留明確部分關聯，不提供整單合計；有容量問題時不得宣告關聯完整。

即使顯示關聯與容量檢查通過，文件仍明確禁止正式報價、確認及保存。完整來源原文、正式核准結果與兩次確認紀錄仍須在未來正式快照文件中整合，不能把本批演練檔當成正式快照。

## 5. 待 DBA 核准的加法式關聯設計

契約集中在[獨立表結構草案](../database/multi_snapshot_schema.py)，不註冊到應用程式的啟動建表中。

| 資料表 | 主鍵／唯一性 | 用途 |
|---|---|---|
| [既有完整文件表](../database/models.py:284) | 事業別＋預覽識別；事業別＋正式單號唯一 | 保留完整固定文件及內容摘要；既有文件不改寫 |
| [既有快照明細表](../database/models.py:228) | 事業別＋正式單號＋全單序號 | 保留原主鍵與所有既有欄位，不改以部位路徑作主鍵 |
| [新產品明細表草案](../database/multi_snapshot_schema.py:17) | 事業別＋正式單號＋產品明細識別；同單展示順序唯一 | 產品層版本、名稱、數量及展示順序；以同單外鍵指向完整文件 |
| [新列歸屬表草案](../database/multi_snapshot_schema.py:35) | 事業別＋正式單號＋全單序號；同單產品明細＋路徑唯一 | 每個快照列只能歸屬一筆產品，同時指向原快照列與同單產品明細 |

約束均包含事業別與正式單號，避免跨事業別或跨單引用。產品順序及數量必須大於零，明細修訂版不得為負值。

舊快照不要求補建新關聯。未來讀取入口必須按正式文件版本分流：舊版依原文件讀取，不重算、不回填；新版才要求全部產品與列關聯完整。**正式新版文件的生成、保存及讀取分流尚未接通，本批不建立假正式版本。**

資料庫外鍵只能保證被引用列存在，不能單獨證明新列歸屬表的路徑等於原快照列路徑，也不能強制新版每列都必須有關聯；未來正式保存服務須以同版完整文件核對雙向覆蓋後，在同一交易寫入。不可只以資料表約束取代應用層驗證。

## 6. 遷移與保存的後續核准項目

本批提供[待審查 DDL 文字產生器](../database/multi_snapshot_schema.py:53)，僅編譯 SQLite／MySQL／MSSQL 的兩張新增表，不接受連線、不執行 SQL。不得直接把草案視為正式遷移。

正式開放前須完成：

1. 備份正式資料並完成還原演練，記錄資料庫版本、字元集、定序與索引政策。
2. 由 DBA 核對現場既有表與 ORM 的差異，確認複合唯一鍵、欄位寬度與外鍵可用；MySQL 須確認交易引擎及字元編碼。
3. 核准正式多明細文件版本、來源／核准資料內容、預覽摘要及不可混用的讀取契約。
4. 明確遷移只新增核准表，不依應用啟動建表改動既有表；不重算歷史、不批次重寫舊資料。
5. 完整文件、產品明細、成本列與列關聯由同一保存服務、同一交易寫入。
6. 以正式預覽識別實作冪等保存、並行唯一鍵競爭後重試、內容衝突拒絕及全部回滾；不能只測表結構就認定正式保存已完成。
7. 定義停用新功能與回退方案；已有新版本資料時不能直接刪表，須先備份與確認舊程式不會誤讀新版。
