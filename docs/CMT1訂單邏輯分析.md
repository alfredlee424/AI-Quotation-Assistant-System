# CMT1 訂單邏輯分析規格

> 2026-09-18 更新：成本必須除以裁切量。新報價的實作與部署契約見
> [固定版本報價流程](固定版本報價流程.md)。歷史訂單驗證與「依現行主檔重報」為兩種不同操作。

本文件依 `test/ord.txt`、`test/ordstr.txt`、`test/ordspe.txt`、`test/ordspd.txt`、`test/ordqty.txt` 的實際資料回推，作為 TXT 匯入、訂單驗證與報價／訂單快照實作的基準。

## 1. 五個資料檔的角色

| 檔案 | 角色 | 主要 Key | 說明 |
|---|---|---|---|
| `ordspd.txt` | 選項類別定義 | `workgroup + optno` | 例如 `A001=桌面尺寸`、`B001=木腳尺寸`、`W001=工費` |
| `ordstr.txt` | 結構樹／必選規則 | `workgroup + pathf + pathc` | 每列是父路徑到子路徑的邊，`must_chose` 與 `seq` 控制必選和順序 |
| `ordspe.txt` | 規格與採購成本 | `workgroup + path + code` | `codsc` 是規格名稱，`compri` 是採購成本；同一 code 在不同 path 可代表不同規格 |
| `ordqty.txt` | BOM 用量規則 | `workgroup + path + code` | `stdqty`、`stdpar` 依部件路徑及驅動規格代碼決定；`codsc` 在實際資料為 NULL |
| `ord.txt` | 正式訂單明細快照 | `workgroup + ref_no + path`（實務上同一路徑可因明細而重複） | 已把規格、用量與成本寫入訂單，不應用目前主檔重算歷史訂單 |

## 2. 路徑規則

產品前綴為 `CMT1`。完整路徑格式如下：

```text
CMT1\{根選項}\{子選項}...
```

以 `ordstr` 的 `pathf` 查詢 `pathc`，依 `seq` 遞迴展開。`pathc` 若不再出現在任何 `pathf`，就是葉節點；葉節點是計價候選，但訂單快照仍可保存所有結構節點。

同一產品有多棵獨立驅動樹：

```text
CMT1\A001  桌面尺寸
CMT1\B001  木腳尺寸
```

查詢 `ordqty` 時，A001 樹下的部件使用 A001 選取代碼，B001 樹下的部件使用 B001 選取代碼。不能以子部件自己的材料代碼取代驅動代碼。

## 3. 訂單明細欄位推定

`ord.txt` 每列為 13 欄，依實際資料推定為：

```text
workgroup, ref_no, path, qty, spc_code, spdsc,
stdqty, stdpar, compri, abndat, abntim, usrno, prgno
```

其中 `qty` 是該訂單明細的實際用量／件數，不能直接假設為整張訂單的產品數量；例如 `S030` 的 `qty=2` 可表示兩個圓孔。產品訂購總數目前不在五個檔案中，若需要保存，應放在訂單主檔或額外欄位，不能從每一列反推。

## 4. 展開與計價流程

```text
產品 CMT1
  -> ordstr 展開結構樹
  -> 對每個訂單 path 以 ordspe 驗證 code / codsc / compri
  -> 依用量表指定的驅動部位及所選尺寸查用量
  -> 成本 = 明細數量 × 用料量 ÷ 裁切量 × 採購單價
  -> 保存固定版本預覽
  -> 人工確認後保存相同版本快照，不重新查價
  -> 已成立訂單直接使用歷史快照欄位
```

零價結構節點仍保存於快照。不能僅按葉節點計價：歷史隔板父節點也可能有自己的費用。
歷史數值不覆寫；UI 貼上匯入明確屬於「以現行主檔重報」，另行輸入產品數量，來源列保留作參考。

60×180 桌面立水：4.5 ÷ 24 × 700 = 131.25。
QU26821001-01001 按歷史明細快照計算：桌面 3,257.75＋木腳 751.333…＝4,009.08。
此值不能直接當成現行主檔新報價的預期值。

## 5. 驗證規則

1. 五個檔案的 `workgroup` 必須一致，CMT1 路徑必須以 `CMT1\` 開頭。
2. `ordstr.pathc` 的父節點必須能由 `pathf` 連接；循環路徑要報錯。
3. 訂單有規格代碼時，必須能在 `ordspe(workgroup,path,code)` 找到；名稱不同只能警告，因歷史名稱可能已變更。
4. `ordqty` 以 `(workgroup,path,driver_code)` 查詢；查不到時不可靜默把歷史訂單的用量改成 `1.0`。
5. `ord.txt` 的歷史 `stdqty/stdpar/compri` 與目前主檔不同時，只標記 drift，不修改訂單快照。
6. `ordstr.must_chose=Y` 的節點若未出現在訂單，對新報價列為缺項；歷史訂單只列為資料完整性警告，以免舊單因主檔新增必選項而無法讀取。

## 6. 已知不確定事項

- `ord.txt` 第 4 欄雖可由資料型態解讀為明細 `qty`，但正式 ERP 欄位名稱仍應以 `ord940`／實際 DDL 確認。
- `ordqty.stdqty` 與 `ord.txt` 的數值在部分 B001 明細存在差異；因此匯入器必須保留兩者並報告差異，不能直接假設其中一方錯誤。
- 五個檔案沒有產品訂購總數主檔，因此 `ref_no` 下的總數只能由外部訂單主檔提供。
