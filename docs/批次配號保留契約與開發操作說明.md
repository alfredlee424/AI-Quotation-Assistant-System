## 1. 2026-10-02 交付界線

- 開發請求：[`DevelopmentReservationRequest`](../engine/quote_number_reservation.py:54) 與 [`DevelopmentReservationChild`](../engine/quote_number_reservation.py:42)。這是底層保留測試契約，不是「已核准正式預覽」型別。
- 表定義：[`reservation_schema()`](../database/quote_number_reservation_schema.py:10)。不加入正式模型集合，也不複製、修改或回填歷史表。

## 2. 格式、順序與唯一性

1. 同批前綴為台灣時區的 14 位年月日時分秒，再接底線及 001 至 999 的三位尾碼，完整長度 18。例如 20261002083045_001。不使用隨機尾綴，不修改格式。
2. 前綴由具時區的時鐘值轉成台灣時區；UTC 輸入會正確跨日。微秒不進單號。無時區時間拒絕，不猜作本機或 UTC。
3. 依完整固定請求中的子報價順序配置，從 001 起，不重排、不按路徑合併、不按成品件數拆單。四品項、2／1／6／2 件為四個保留號，不是 11 個。
4. 空批與超過 999 張整批拒絕，不截斷、循環或暗中另拆批次。原內部金額試算的 200 張資源上限不因此變成 999 張。
5. 批次識別、請求識別、預覽識別各自獨立；穩定子報價、來源品項及配置識別另外保存。既有每張成本列仍使用自己的五位序號；三位尾碼不取代成本列序號。
6. **同一 registry 全域前綴唯一，不按事業別分割**；完整保留號也有全域唯一鍵。因此不同批次即使不同事業別，也不得拿到相同完整號。批次、請求及預覽身份也分別全域唯一。
7. 「全域」指同一權威 registry 資料庫，不是多個互不相連副本。未來所有正式配號節點必須共用同一 registry；跨副本、多主及災難回復配號尚未驗收。不能各自建庫再宣稱跨庫唯一。

## 3. 配號時機與未來正式流程

定稿的銜接順序如下，**本批尚未接上這個正式流程**：

1. 未來正式服務先驗證整批全部来源、需求、條件、圖面、規格、用量、金額及核准身份；任一張不通過即停止，不呼叫保留服務。
2. 固定完整的未配號內容、全部順序、版本及穩定批次／請求／預覽識別。內容須包含來源全文與座標、配置、成品數、逐張金額／成本證據、批次總計、規則、圖面及核准紀錄，不能只傳來源摘要或品項數。
3. **在第一次人工確認之前保留整組**。保留服務以一次交易寫入 header 與所有子報價對應；保留成功後，正式預覽才可把原固定內容與整組保留對應共同納入最終指紋並展示。
4. 两次確認均須綁定同一份完整正式預覽（含全部保留號及對應），不能只確認批次總額或單一張。保留成功不跳過任何確認或工程關卡。
5. 第二次確認後，T29 未來服務驗證同一不可變保留，並以另一個完整交易保存正式批次、全部子報價、關聯及成本列。不循環呼叫會各自提交的單品保存。
6. 正式保存失敗，正式資料全回滾；先前已成功的保留仍留下，不回收。正式開立狀態應由未來正式保存／開立關聯表證明，不靠把本批不可變保留狀態改成「已開立」。

預覽內容與最終含號指紋須分層，避免把尚未產生的號碼納入保留請求而形成循環摘要。這是 T28／T29 的銜接契約，不是已實作的正式預覽建構器。本批不接受現有非正式描述或新舊內部試算文件直接轉型；它們的不可確認狀態不會因保留服務存在而解除。

## 4. 完整固定請求與不可變性

開發請求保存事業別、來源批次／工單、批次修訂、請求／預覽識別、來源程式紀錄、完整固定上下文及有序子報價。每個子項保存同批／同事業別／同來源工單引用、穩定來源／子報價／配置識別、正整數成品數及完整固定內容。

- 固定上下文及每張內容使用不可變 JSON 字串；必須是非空物件，拒絕重複鍵及非有限數值。資料轉成完整請求文件並計算 SHA-256，**重試同時比對完整文件，不只相信呼叫者宣稱的摘要**。
- 字串採保守逐字相等政策：即使內層 JSON 僅空白／鍵排列改變，也視為不同固定內容。呼叫端應保存並重送原請求，不重新序列化猜測原內容。
- 低層只驗證開發型別、身份歸屬、唯一對應、數量、版本及固定內容完整保存，不理解 JSON 內的業務核准是否足夠，也不認證操作人。摘要不是簽章，來源程式欄位不是登入身份。
- 正式入口未來必須負責語意完整性與授權，不能拿任意非空 JSON 加一個「通過」旗標呼叫這個底層服務來宣稱正式核准。
- 同批、同請求、同預覽與完全同內容重試，返回原整組，**先查 registry，不讀配號時鐘**；跨日、時鐘暫時失準或重建服務／引擎後仍可取回。
- 同一身份但內容、來源、事業別、順序、數量、版本或預覽識別改變，明確拒絕，不誤用舊號。新請求識別也不能覆寫已有批次保留。
- **新預覽政策採保守拒絕**：已有保留的批次不能換預覽。真正修改後須由未來受控流程建立新的批次及相應子報價／請求／預覽身份（必要時新草稿），保留舊批次的追溯關聯；不能暗中修改現有穩定身份生成規則或回收舊號。
- 重試會核對已保存 header、摘要、全部有序子項、時間及前綴。資料缺失／被改寫時安全拒絕，不補配缺張、不重新編號。

服務只提供追加保留及冪等查回，沒有修改、刪除、重排或回收 API。成功保留後即使未確認、取消、程序中斷、使用者離開或正式保存失敗，都作孤兒保留永久保留；允許缺號，不把缺號當成需要補回的故障。SQL 管理權仍可破壞資料，正式部署須另外核准只允許必要讀取／新增的權限、稽核與不可變保護；目前沒有宣稱跨資料庫不可變觸發器已部署。

## 5. 原子競爭、時鐘與有界失敗

- 時間字串不是唯一保證。先讀取已有身份，再依資料庫唯一鍵競爭插入 header；同交易逐張插入，全部成功才提交。第 2／4 張失敗都會回滾 header 與已插入子項。
- 只辨識 SQLite 已知 header 身份／前綴唯一鍵為可重試競爭；先回滾，再重新查身份。同請求競爭回原組；不同批次前綴衝突則等待真實時鐘進入下一秒，再重新讀時鐘。
- 不把前綴加一秒、不製造未來時間；停止不動的時鐘只會有限失敗。預設 monotonic deadline 為 2 秒、最多 50 次、輪詢間隔最多 0.05 秒，睡眠不超過剩餘預算；即使注入的 monotonic 不前進，attempt 上限仍能停止。
- registry 已有比新配號時鐘更新的前綴時，安全拒絕；單次等待過程內 wall clock 倒退（含同秒微秒倒退）或 monotonic 倒退／非有限值也拒絕。跨重啟只以持久前綴的秒精度高水位判定；它不是可信授時或跨主機時鐘校正系統。
- 等待前已離開連線及交易，不在睡眠期間持資料庫寫鎖。SQLite driver 的鎖等待設為零，忙碌寫鎖使用同一有界迴圈重試，不讓 driver 的長等待取代 deadline。
- 子表唯一鍵、外鍵、CHECK、其他完整性錯誤、非忙碌資料庫錯誤及 sleep 失敗原樣傳出，不吞成前綴碰撞。資料庫不存在／不可用時不初始化、不回傳假成功。
- deadline 控制本服務的重試及睡眠，不強制中斷正在執行的 SQL、連線池 checkout、作業系統磁碟 I/O 或呼叫端注入函式。呼叫端須另設有限連線池／I/O 等待，不能把本版宣稱為硬即時服務。
- 逾時、失敗或提交回應遺失時，請持原完整請求重試。已提交則查回原組，未提交則重新原子競爭；不要生成新身份猜測是否成功。

錯誤型別：[`ReservationConflict`](../engine/quote_number_reservation.py:29)、[`ReservationTimeout`](../engine/quote_number_reservation.py:33)、[`UnsafeClock`](../engine/quote_number_reservation.py:37)。錯誤不代表已開立，也不授權跳過正式流程。

## 6. 獨立 registry 與交易 ownership

| 新表 | 保留內容與約束 |
|---|---|
| [`quote_number_reservation`](../database/quote_number_reservation_schema.py:13) | 全域批次主鍵，請求／預覽／前綴各自唯一；事業別、版本、時間、來源、固定保留狀態、1–999 張數、完整請求及內容摘要 |
| [`quote_number_reserved_child`](../database/quote_number_reservation_schema.py:37) | 同批子報價主鍵、全域子報價及完整保留號唯一；同批來源／配置／順序／尾碼各自唯一；批次＋事業別＋前綴的複合外鍵引用 header |

保留請求的完整来源與內容存在 header 文件，子表是其固定對應的索引；服務驗證兩者一致。沒有引用前批「非正式描述」表來冒充正式批次，也不寫入既有快照或成本表。未來正式文件到保留的複合關聯須在 T29／DBA 審查中加入，不以目前外鍵存在就宣稱正式保存完成。

服務只接受明確的 SQLAlchemy 引擎，不接受外部連線、Session 或已有交易；自己 checkout 新連線、自己持有短交易。SQLite 限檔案型及獨立 checkout 的 QueuePool／NullPool，拒絕會共用單一實體連線的池及記憶體庫，避免另一個 wrapper 誤提交／回滾呼叫端資料。呼叫端在同一正常連線池持有寫交易時，本服务只能有限等待／失敗，不會提交該交易。

隔離引擎須由呼叫端明確啟用 SQLite 外鍵；未啟用會拒絕。不得以繞過檢查、共用任意既有交易或自訂會回傳同一實體連線的池來接入正式服務。

**MySQL／MSSQL 僅編譯 DDL 待審查，服務建構時明確阻擋 runtime**；沒有連线或執行過這兩種資料庫。正式部署仍需核對方言、字元集／定序、欄位長度、唯一鍵錯誤分類、鎖／隔離層級、交易引擎、時區、備份回復、權限與併發測試，不能直接解除方言檢查就上線。部分字串格式由服務驗證，不宣稱跨資料庫 DDL 已能單獨證明全部固定文件語意。

## 7. 開發操作與驗收

1. 使用指定虛擬環境與測試隔離設定。勿從应用正式連線複製引擎、匯入私密環境檔或把私人來源文件當測試資料。
2. 參考測試的隔離引擎 fixture：建立暫存檔案型 SQLite，明確啟用外鍵，僅對兩張新 registry 表明確建表；服務本身從不建表。
3. 建立獨立 typed 開發請求，完整保存固定上下文與有序子項，再把隔離引擎及時鐘／monotonic／sleep 注入服務。測試四品項不是正式預覽範例，更不是向客戶展示的假報價。
4. 呼叫保留後檢查整組對應與不可報價／確認／保存旗標。再次呼叫原請求應取回完全同一文件；更動內容應拒絕。不要把返回文件送進正式單品或批次試算／快照入口。
5. 新增測試命令：[`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 ./venv/bin/python -m pytest test/test_quote_number_reservation.py -q -p no:cacheprovider`](../test/test_quote_number_reservation.py:1)。
6. 完整回歸命令：[`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 ./venv/bin/python -m pytest test -q -p no:cacheprovider`](../test/conftest.py:15)。

2026-10-02 實際結果：本批 **122 項全部通過（1.44 秒）**；指定命令完整回歸 **1269 項全部通過（72.15 秒）**，既有 1147 項維持。最初新增測試的 fixture／入口引用錯誤已修正後重跑，以上為修正後實際結果。

包含兩個獨立引擎／實體連線對同一 SQLite 暫存檔的真實唯一鍵競爭：同請求回原組、不同批次下一秒成功、時鐘不前進的有限失敗、同請求異內容拒絕。其他測試涵蓋 0／999／1000、四張非 11 張、跨事業別、來源／子項重複、跨日與重啟、版本／內容／順序變更、時鐘倒退／無時區、sleep／資料庫失敗、非碰撞完整性錯誤、2／4 張原子回滾、鎖釋放、外部交易不被提交、registry 損壞拒絕，以及單品／新舊內部文件入口隔離。

既有單品快照僅新增文件類型拒絕保護；正常單品預覽／兩次確認／保存語意不變。舊批次描述、舊整單未捨入試算、新逐張金額及歷史快照文件的原契約保留，不重算、不重編已開立號碼。
